# Instructions
AIがPull Requestを作成する際は、必ず `create-pr` スキル（または `/pr` コマンド）を使用し、`.github/PULL_REQUEST_TEMPLATE.md` に従い、以下のルールを**必ず**遵守すること。（直接 `gh pr create` でフォーマット違反のPRを作ろうとした場合はHooksによりブロックされます）

## 基本原則
- テンプレートの全セクションを**省略せず**記載すること。該当しないセクションは「該当なし」と明記する。
- PRタイトルは `[種別] 変更の要約` の形式にすること（例: `[Feature] ユーザー認証APIの追加`）。
  - 種別: `Feature`, `Bugfix`, `Refactor`, `Docs`, `Chore`

## 各セクションの記述ルール

### 変更種別
- **必ず1つ以上**チェックすること。空のまま提出しない。

### 影響範囲
- **必ず1つ以上**チェックすること。変更がどのレイヤーに影響するかを正確に判断する。

### 関連Issue
- **必ず** `Closes #番号` の形式でIssueを紐づけること。`Fixes #番号` や `Resolves #番号` でも可。
- 複数のIssueに関連する場合は `Closes #1, Closes #2` のように列記する。

### 何を変更したか
- 箇条書きで**具体的に**記載すること。
- ファイル名、クラス名、関数名など**具体的な識別子を交えて**記述する。
- 悪い例: `認証機能を追加した`
- 良い例: `backend/app/routers/auth.py に POST /api/auth/login エンドポイントを追加し、JWTトークンを返却する処理を実装した`

### なぜ変更したか
- Issueの要件や背景に基づいて、**変更の動機・目的**を記載する。
- 技術的な判断の理由（「なぜこのライブラリを選んだか」「なぜこの設計にしたか」など）も含める。

### 主な変更ファイル
- テーブル形式で**最低でも主要な変更ファイル3つ**を記載すること（変更ファイルが3つ未満の場合は全て記載）。
- 「変更内容」列には、そのファイルで具体的に何を変えたかを1行で要約する。

### テスト結果
- `make test-all` や `pytest`, `npm run test` などの**テストコマンドを実行**し、結果を「テスト実行ログ」に貼り付けること。
- テストが通らない場合は、その理由と対応方針を備考欄に記載すること。

### 動作確認チェックリスト
- 実際に確認した項目のみチェックを入れること。未確認の項目にチェックを入れてはいけない。

### 備考・スクリーンショット
- UIの変更がある場合は**必ず**スクリーンショットを添付すること。
- `docs/design.md` の更新有無を明記すること（設計変更を伴う場合は必須）。
- レビュアーに特に確認してほしいポイントがあれば記載する。
