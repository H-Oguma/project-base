# Subagent Definitions

本プロジェクトでは、以下の5種類のサブエージェントを `define_subagent` で定義して使用する。
**コスト最適化が最優先**であり、タスクの性質に応じて最も安価なモデルを選択すること。

## コスト階層（安い順）

| モデル | コスト | 選定基準 |
|:--|:--|:--|
| `flash_lite` | 最安 | 単純なファイル読み取り、定型出力のみ |
| `flash` | 安価 | リサーチ・分析・レビュー・テスト実行（**最も頻用**） |
| `inherit` | 標準 | 複雑なコード生成・設計判断 |
| `pro` | 高価 | **ユーザーが明示的に指示した場合のみ使用可** |

---

## 1. 🔍 researcher（コードベースリサーチャー）

- **推奨モデル**: `flash`
- **書き込み権限**: なし（`enable_write_tools: false`）
- **MCP**: 不要（`enable_mcp_tools: false`）
- **役割**: コードベースの調査、grep検索、ファイル内容の確認、Web検索、ドキュメント調査
- **呼び出しタイミング**:
  - 実装前の事前調査（影響範囲、既存実装の把握）
  - 「〜を調べて」「〜はどこにある？」系の質問
  - 技術情報のWeb検索
- **システムプロンプトに含めるべき指示**:
  - 日本語で回答すること
  - 調査結果は箇条書きで構造化して報告すること
  - ファイルパスは必ず絶対パスで報告すること

## 2. 🛠️ worker（実装ワーカー）

- **推奨モデル**: `inherit`（親と同じ）
- **書き込み権限**: あり（`enable_write_tools: true`）
- **MCP**: あり（`enable_mcp_tools: true`）
- **役割**: コードの実装・編集、テストの作成、コマンド実行、ファイル作成
- **呼び出しタイミング**:
  - フロントエンド/バックエンドの機能実装
  - テストコードの作成
  - 設計書（`docs/design.md`）の更新
  - 並列作業時（frontend worker と backend worker を同時起動可）
- **システムプロンプトに含めるべき指示**:
  - `.agents/rules/` 配下のルール（セキュリティ、TDD、ドキュメント）を遵守すること
  - 日本語でコメント・ドキュメントを記述すること
  - 仮想環境・Dockerを使用すること
  - 作業完了時は変更ファイル一覧と要約を報告すること

## 3. 📋 reviewer（コードレビュアー）

- **推奨モデル**: `flash`
- **書き込み権限**: なし（`enable_write_tools: false`）
- **MCP**: 不要（`enable_mcp_tools: false`）
- **役割**: 実装済みコードのレビュー、バグの検出、セキュリティチェック、ベストプラクティスの確認
- **呼び出しタイミング**:
  - **PR作成前の必須レビュー**（ワークフロールールで義務化されている）
  - セキュリティ観点のスポットレビュー
  - リファクタリング後の品質確認
- **システムプロンプトに含めるべき指示**:
  - `.agents/rules/security.md` のセキュリティ基準に照らしてレビューすること
  - 指摘事項は「重大度（Critical/Warning/Info）」「ファイル名:行番号」「指摘内容」「修正提案」の形式で報告すること
  - 問題がなければ明示的に「LGTM（問題なし）」と報告すること

## 4. ✅ tester（テストランナー）

- **推奨モデル**: `flash`
- **書き込み権限**: あり（`enable_write_tools: true`、コマンド実行のため）
- **MCP**: 不要（`enable_mcp_tools: false`）
- **役割**: テストの実行、結果の分析、カバレッジの確認、CI前のローカル検証
- **呼び出しタイミング**:
  - 実装完了後のテスト実行
  - PR作成前の最終テスト確認
  - テスト失敗時の一次切り分け
- **システムプロンプトに含めるべき指示**:
  - `Makefile` のコマンド（`make test-all`, `make lint` 等）を使用すること
  - テスト結果は「合格/不合格」「失敗したテスト名」「エラーメッセージ」を構造化して報告すること
  - 仮想環境・Dockerを使用すること

## 5. 📝 planner（設計アドバイザー）

- **推奨モデル**: `inherit`（親と同じ）
- **書き込み権限**: なし（`enable_write_tools: false`）
- **MCP**: 不要（`enable_mcp_tools: false`）
- **役割**: 設計方針の立案、アーキテクチャの相談、技術選定のアドバイス、タスク分解
- **呼び出しタイミング**:
  - 新機能の設計時
  - 技術的な意思決定の壁打ち
  - 複雑なタスクの分解計画
- **システムプロンプトに含めるべき指示**:
  - プロジェクトの技術スタック（React 19, FastAPI, SQLAlchemy等）を前提とすること
  - 提案は「案1/案2」のように複数提示し、メリット・デメリットを比較すること
  - セキュリティと保守性を優先すること

## 運用ルール

### サブエージェントの再利用
- 新しいサブエージェントを呼ぶ前に、`manage_subagents` (list) で既存の idle サブエージェントを確認すること。
- 同じ種別の idle サブエージェントがあれば `send_message` で再利用する。

### 並列実行の方針
- `worker` は並列起動を許可する（例: frontend worker + backend worker）。
- それ以外のサブエージェントは原則1体ずつ呼び出す。

### リソース解放
- 用が済んだサブエージェントは速やかに `manage_subagents` (kill) で終了させる。

### pro モデルの使用制限
- `pro` モデルは**ユーザーが明示的に指示した場合のみ**使用可。
- エージェントの自主判断で `pro` を選択してはならない。
